# ServicePulse v0.8.0 — Incident Detection & Webhook Alerting

Prepared release notes; this version has not yet been tagged or released.

- Configure a positive failure threshold per service, defaulting to three, plus an optional HTTP/HTTPS webhook URL.
- Persist consecutive failures and open one incident when the threshold is reached. Continued failures retain the incident; recovery resets the streak and resolves it.
- Query incident history through `/api/incidents`, `/api/incidents/{id}` and `/api/services/{serviceId}/incidents`, with optional status filtering on the global list and derived resolved duration.
- Send opening and recovery webhooks only after the incident transaction commits. Repeated failed checks do not repeatedly alert.
- Isolate delivery errors with one bounded attempt, safe logging and outcome metrics. No retries, queues, outbox or replay are included; delivery is best-effort, not guaranteed or ordered.
- Expose incident-opening totals, the current open-incident count, and delivery outcomes through the existing Prometheus endpoint, without service-specific labels.
- Expand coverage from 73 to **113 passing automated tests**, including concurrent checks, rollback suppression, threshold boundaries, restart persistence, local webhook delivery and interruption.

Existing APIs, HTTP status policy, check metrics, uptime calculations, Docker configuration and CI checks remain intact. Existing registrations receive threshold 3, zero consecutive failures and no webhook; previous checks are preserved without retroactive incidents. There is no service-deletion API or cascading history deletion.

URLs must be trusted: private networks remain reachable and webhook payloads are unsigned. PostgreSQL, authentication, MTTR/statistics APIs, retry infrastructure and external integrations remain outside this release.
