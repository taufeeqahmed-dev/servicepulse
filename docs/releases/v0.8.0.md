# ServicePulse v0.8.0 — Incident Detection & Webhook Alerting

ServicePulse v0.8.0 adds incident detection and best-effort webhook alerting to manual and scheduled monitoring.

- Configure a positive integer failure threshold per service, defaulting to three when omitted or null, plus an optional HTTP/HTTPS webhook URL. Fractional, string and out-of-range thresholds are rejected.
- Persist consecutive failures and open one incident when the threshold is reached. Continued failures retain the incident; recovery resets the streak and resolves it.
- Query incident history through `/api/incidents`, `/api/incidents/{id}` and `/api/services/{serviceId}/incidents`, with optional status filtering on the global list and derived resolved duration.
- Send opening and recovery webhooks only after the incident transaction commits and releases its persistence resources. Repeated failed checks do not repeatedly alert. Caller cancellation is preserved across database lock waits, suppresses webhook delivery and stops further batch work after recording commits or rolls back; interrupted HTTP attempts are still recorded.
- Isolate delivery errors with one bounded attempt and outcome metrics. Webhook logs omit URLs and exception text; scheduler failures log safe identifiers and exception types without nested persistence exceptions that can contain credentials. No retries, queues, outbox or replay are included; delivery is best-effort, not guaranteed or ordered.
- Expose incident-opening totals, the current open-incident count, and delivery outcomes through the existing Prometheus endpoint, without service-specific labels.
- Expand coverage from 73 to **138 automated tests**, including database-observed lock contention, concurrent manual/scheduled checks, commit-failure and rollback-only suppression, strict threshold boundaries, the complete v0.7 upgrade/restart workflow, connection-pool release, client timeout/socket closure, cancellation during HTTP/lock/admission waits, bounded persistence concurrency, graceful worker/application shutdown and credential-safe scheduler failure logging.

Existing APIs, HTTP status policy, check metrics, uptime calculations, Docker configuration and CI checks remain intact. Existing registrations receive threshold 3, zero consecutive failures and no webhook; previous checks are preserved without retroactive incidents. There is no service-deletion API or cascading history deletion.

URLs must be trusted: private networks remain reachable and webhook payloads are unsigned. PostgreSQL, authentication, MTTR/statistics APIs, retry infrastructure and external integrations remain outside this release.
